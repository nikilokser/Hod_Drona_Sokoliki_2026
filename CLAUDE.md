# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Проект

Подготовка команды к очному этапу соревнования «Ход дрона: шахматные сражения роёв» (2026).
Суть: автономный «шахматный» матч двух гетерогенных роёв робототехнических аппаратов
(летающие дроны + наземные роверы), где ход выбирают LLM-агенты через переговоры
(шахматные движки запрещены). Основная задача, которую предстоит реализовать — веб-фронтенд
(«веб морда») для управления/наблюдения за процессом: поле, состояние партии, лента переговоров
агентов, таймер хода, счёт/штрафы и т.д. Детали фронтенда уточняются у пользователя по ходу работы.

Полный регламент лежит в `Регламент_очного_этапа_Ход_дрона_20261.pdf`. Ниже — выжимка того,
что реально влияет на архитектуру, плюс вводные, которых нет в самом регламенте.

## Ключевые ограничения регламента

- Аппараты действуют полностью автономно, без ручного управления в реальном времени.
  Единственное вмешательство человека — аварийный Kill Switch (обязателен на каждом БПЛА).
- Выбор хода — **исключительно** через взаимодействие LLM-агентов. Шахматные движки
  (Stockfish, Leela и т.п.) запрещены. Обмен данными между командами во время матча запрещён.
- Каждый аппарат — отдельный LLM-агент, **кроме роверов-пешек**: все пешки команды
  управляются одним LLM-агентом-диспетчером, разработанным участниками.
- На аппаратах должна быть архитектура OpenClaw или аналогичная агентная, подключённая
  к облачному/локальному LLM-провайдеру.
- Переговоры агентов при выборе хода обязаны отображаться на экранах команды.
- Лимит одного хода — 5 минут (таймер стартует после полного завершения хода соперника
  и фиксации судьёй). Лимит матча — 2 часа.
- Состав на зачётный матч: 6 дронов (Король, Ферзь, 2 Слона, 2 Коня), 8 роверов-пешек,
  2 ровера-ладьи. Всего 16 аппаратов на сторону, парк организаторов — 32 (2 полных комплекта).
- Дрон: полётный контроллер PX4 + Raspberry Pi (компьютер-компаньон) + optical flow
  с дальномером + камера. Платформа предоставляется организаторами («Сверх»), свои аппараты
  использовать нельзя.
- Поле: игровая доска 4×4×1 м с ArUco-маркерами в клетках, внутри лётной зоны-куба 8×8×4 м.
  Аппарат должен помещаться в одну клетку (≤0,5×0,5 м).
- Лимиты: высота полёта ≤4 м, скорость дрона ≤2 м/с, скорость ровера ≤1 м/с.
- Упрощённые шахматы: без рокировки, взятия на проходе, превращения пешки, повторения позиции,
  правила 50 ходов. Ничьи нет.
- Ошибки хода:
  - невозможный ход (LLM) → штраф -5, таймер хода сбрасывается; после 3 подряд —
    ход один раз выполняет «судейский алгоритм» (баллы за такой ход не начисляются);
  - превышение 5-минутного лимита → штраф -10, ход выполняет судейский алгоритм;
  - ошибка физического выполнения корректно выбранного хода → штраф, ручной перенос фигуры
    судьёй.
- Баллы: ход вовремя +1, взятие пешки +10, коня/слона +30, ладьи +50, ферзя +90, мат — победа.
  Бонус за «продвинутое использование LLM» до +30 (на усмотрение судейской коллегии).
  Штрафы: невозможный ход -5, просрочка хода -10, физический контакт вне взятия -20.
- Победа — мат; при пате или истечении лимита времени матча — по сумме баллов.

## Технические вводные (не из регламента, от пользователя)

- **Дроны — ROS1.**
- **Роверы (ладьи) — ROS2.**
- **Пешки — на ESP-платах** (без ROS), управляются через LLM-агента-диспетчера пешек.
- На роверах и дронах, по всей видимости, уже развёрнут какой-то агентный стек «из коробки»
  (см. упоминание OpenClaw в регламенте) — перед началом реализации стоит выяснить, что именно
  там уже есть, чтобы не дублировать. Подтверждено репозиторием ниже: инфраструктура связи уже
  существует и предоставлена организаторами.

## Инфраструктура связи, предоставленная организаторами

Орги прислали два материала, которые описывают уже существующую (не нашу) инфраструктуру:

- **`MULTI_DRONE_SETUP.md`** (в этом репозитории) — инструкция по разворачиванию нескольких
  клонов образа SD-карты дрона (ROS1 Noetic, `catkin_ws`, MAVROS/PX4). У каждого дрона свой
  `FLEET_ROBOT_ID`, hostname, machine-id, SSH-ключи. На дроне крутится либо `pseudo`-агент
  (заглушка для проверки без LLM), либо `agent` (реальный LLM-агент, нужен `OPENAI_API_KEY`),
  переключается через `DRONE_AGENT_MODE` в systemd override. Локализация — по общей ArUco-карте
  `chess_8x8_main.txt` (`CHESS_MAP_FRAME_ID=aruco_map`, `CHESS_CELL_SIZE_M=0.40`,
  `CHESS_ARRIVAL_TOLERANCE_M=0.20`). Явно указано: текущие ROS-пакеты **не** решают
  избежание столкновений, резервирование клеток и общую диспетчеризацию воздушного
  пространства — это ответственность команды.
- **[dark516/sverk_ai_communication_server](https://github.com/dark516/sverk_ai_communication_server)**
  — готовый центральный сервер связи («СВЕРХ AI Agents Server»), уже реализующий именно то,
  что мы планировали городить через свой TCP. Состав: FastAPI Gateway + MQTT-брокер (Mosquitto,
  Docker Compose) + простой web-чат + реестр роботов + JSON Schema протокол + симулятор
  16 фейковых роботов для отладки без железа.

  **Топология:** `config/fleet.yaml` перечисляет весь парк с `robot_id`, типом и IP:
  `peshka-01`…`peshka-08` (`type: peshka`, только IP — без ROS), `rover-01`/`rover-02`
  (`type: ros2_rover`, свой ROS_DOMAIN_ID), `drone-01`…`drone-06` (`type: ros1_drone`, свой
  `ROS_MASTER_URI`, т.к. у каждого дрона собственный roscore). Ровно совпадает с ростером
  зачётного матча (6 дронов / 2 ладьи-ровера / 8 пешек).

  **Транспорт:** MQTT, топики `fleet/v1/robots/<robot_id>/{command,answer,status,availability}`.
  Бортовой мост подписан на `.../command` (JSON: `message_id`, `robot_id`, `text` — свободный
  текст, не структурированная команда) и публикует `.../answer` (`status: completed|error`,
  `text`), опционально `.../status` (промежуточные апдейты) и `.../availability` (online/offline).

  **Gateway REST API (FastAPI, порт 8080, `/docs` — Swagger):**
  - `POST /api/v1/messages` — отправка текста одному/нескольким роботам (`robot_id`,
    `robot_ids`, и/или `@mentions` прямо в тексте), с опцией `wait_for_answer` +
    `answer_timeout_sec`. Это канал «главного агента» (`sender=main_agent`).
  - `POST /api/v1/chat/send` — то же самое, но от имени человека (`sender=user`) через
    веб-чат `@rover_01`, `@everyone` и т.д.
  - `GET /api/v1/robots`, `/api/v1/robots/online`, `/api/v1/robots/{id}` — реестр и online-статус.
  - `GET /api/v1/chat/history` и `WS /api/v1/chat/ws` — история и live-лента всех событий
    (command/answer/status/availability). История хранится только в памяти шлюза, без БД,
    и теряется при перезапуске.
  - Готовый web-чат уже есть на `/chat` (лево — человек/главный агент, право — ответы роботов).

  **Важный вывод:** это **не** протокол переговоров нескольких LLM-агентов между собой —
  это request/response текстовый мост «отправитель → один робот → его текстовый ответ».
  Переговоры между агентами фигур (совместная выработка хода) — это то, что команде всё ещё
  нужно построить поверх этого моста (например, серией вызовов `/api/v1/messages` к разным
  `robot_id` и сведением ответов в одном месте), а не то, что шлюз делает сам.

## Принятые решения по реализации (обновлено с учётом инфраструктуры выше)

- **Позиции фигур на старте — хардкод** в состоянии партии, без реальной ArUco-локализации
  на первом этапе.
- **Перемещение фигур в веб-морде — вручную мышкой** (drag-and-drop по доске). Это не временный
  фолбэк на случай отсутствия трекинга, а сознательное решение: реальный протокол/трекинг
  будет добавляться позже, ручное перемещение должно остаться рабочим способом менять состояние
  партии в UI.
- **Судейский алгоритм (авто-ход при просрочке/3 невозможных ходах) — пока не реализуем**,
  сознательно отложено за скобки текущей работы.
- **Транспорт связи — TCP поверх Wi-Fi для всех аппаратов**, по предложению пользователя. Но
  для связи «главный агент/веб-морда ↔ бортовой агент робота» уже есть готовый рабочий канал
  (MQTT + Gateway REST/WS выше, от организаторов) — вероятно, стоит переиспользовать его вместо
  своего TCP, чтобы не дублировать то, что уже работает. Решение не поменяно, только
  зафиксировано как открытый вопрос ниже — пользователь ещё не подтвердил, что делаем именно так.

## Открытые вопросы (уточнить у пользователя до/во время реализации)

- Использовать ли готовый Gateway (MQTT + REST/WS) организаторов как основной транспорт вместо
  собственного TCP, раз он уже покрывает command/answer/status/availability и даёт бесплатную
  ленту событий для веб-морды (`/api/v1/chat/history`, `/api/v1/chat/ws`)?
- Как в перспективе определяется позиция фигур на доске для UI и логики партии (ArUco с камеры
  дрона / внешняя система трекинга) — отложено, пока хардкод + ручной drag-and-drop.
- Что уже развёрнуто на дроне «из коробки» — пользователь сам запускает дрон и смотрит, что там
  есть, прежде чем двигаться дальше с реализацией. Не начинать кодить агентную часть, пока не
  будет этой информации.
- Кто и как реализует переговоры между LLM-агентами фигур поверх Gateway (свой оркестратор,
  использующий `/api/v1/messages` к каждому роботу, или что-то ещё)?

## Веб-фронтенд (основной deliverable)

Требуется веб-интерфейс, минимально включающий (детали уточняются у пользователя):
- визуализацию поля/доски и позиций фигур;
- ленту переговоров LLM-агентов (обязательное требование регламента — вывод на экран);
- индикатор текущего хода и таймер (лимит 5 мин / до 2 ч на матч);
- счёт и штрафы команды;
- статус Kill Switch по каждому аппарату.

На момент написания этого файла код проекта ещё не создан — репозиторий содержит только PDF
регламента.
