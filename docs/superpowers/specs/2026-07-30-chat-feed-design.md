# Дизайн: лента переговоров (v1)

Дата: 2026-07-30

## Контекст и цель

Регламент обязывает демонстрировать переговоры LLM-агентов на экранах команды во
время матча — это требование допуска, а не украшение (см. `CLAUDE.md`, «Ключевые
ограничения регламента»). Никакого собственного оркестратора переговоров между
LLM-агентами фигур пока не существует — эта задача **не** его строит. Речь только
об отображении сырых событий `command`/`answer`/`status`/`availability`, которые
уже собирает Gateway организаторов (`sverk_ai_communication_server`) через
`GET /api/v1/chat/history` и `WS /api/v1/chat/ws` (формат `ChatEvent`, см.
`CLAUDE.md`, раздел «Инфраструктура связи»).

Это первая из трёх согласованных с пользователем крупных фич (после неё — таймер
хода/матча, затем интеграция Stockfish).

## Область действия

Включено: получение и отображение единой хронологической ленты событий Gateway,
в стиле его собственного `/chat` (слева исходящие, справа входящие, системные
события — по центру), с сохранением на диск, переживающим перезапуск нашего
бэкенда.

Не входит в scope: интерпретация/группировка «кто с кем договаривался»,
фильтрация по роботу (сознательно отложено — одна общая лента без фильтров для
v1), собственный оркестратор переговоров LLM-агентов.

## Архитектура

Наш `web/backend` — единственный, кто ходит в Gateway (тот же принцип, что и для
`send_fly_command`/`get_robots`): браузер никогда не подключается к Gateway
напрямую. Новый модуль `chat_feed.py`:

- Фоновая задача, запускаемая при старте FastAPI (`@app.on_event("startup")`,
  `asyncio.create_task`) и останавливаемая при `@app.on_event("shutdown")`.
- При (пере)подключении сначала подтягивает `GET /api/v1/chat/history` (через
  `httpx`, тем же стилем что `gateway_client.get_robots`), затем открывает
  `WS /api/v1/chat/ws` (библиотека `websockets`, уже используется на нашей
  стороне сервера — здесь используется как клиент) и слушает живые события.
- При обрыве соединения — бесконечный цикл переподключения с задержкой (3 с),
  как уже сделано на фронтенде для нашего собственного `/ws`
  (`connectWebSocket` в `board.js`). Недоступность Gateway не должна приводить
  к падению нашего процесса — уже существующий индикатор «Gateway: …» в тулбаре
  (сейчас управляется поллингом `/api/robots`) достаточен как индикатор
  проблемы, отдельный индикатор для ленты не нужен.

## Данные и персистентность

- `app_state["chat_events"]` — список событий `ChatEvent` как есть (без
  переформатирования), в хронологическом порядке, обрезаемый до последних
  `MAX_CHAT_EVENTS_IN_MEMORY = 1000` записей (защита от разрастания payload,
  который целиком уходит в каждый broadcast — принятое упрощение v1, без
  оптимизации до дифов).
- Локальный файл `web/backend/config/chat_history.jsonl` — построчный JSON
  (JSON Lines), одна строка на событие, дозаписывается (append), **не**
  обрезается и не перезаписывается целиком (дёшево, полезно как полный лог
  матча). При старте бэкенда лента сначала восстанавливается из этого файла
  (`load_chat_events`), затем досинхронизируется через `GET /api/v1/chat/history`
  при первом успешном подключении к Gateway.
- Дедупликация по `event_id`: и история с Gateway, и восстановление из файла, и
  живые WS-события идут через одну функцию `merge_event(app_state, event, path)`,
  которая не добавляет уже известный `event_id` повторно (ни в память, ни в файл).

## API и фронтенд

Отдельный REST-эндпоинт не нужен: `chat_events` — часть `app_state`, которая уже
целиком уходит клиентам через существующий `manager.broadcast` и при первом
подключении к `/ws` (`ConnectionManager.connect` уже шлёт полное состояние).

Новая панель «Лента переговоров» **сбоку от доски** (не под тулбаром, как
панель привязки роботов) — общий layout меняется на двухколоночный
(`board-area` слева, панель ленты справа; на узких экранах панели складываются
в столбец через `flex-wrap`). Внутри самой панели — два столбца по
`event.direction`: `outgoing` (человек/главный агент) слева, `incoming` (ответы
роботов) справа; `system`-события (`availability`, `status`, ошибки) — узкой
строкой по центру на всю ширину панели, приглушённым цветом. Каждая карточка:
время, отправитель/`robot_id`, текст. Автопрокрутка к последнему событию при
получении нового.

## Обработка ошибок

- Gateway недоступен при старте бэкенда — лента просто восстанавливается из
  локального файла, фоновая задача продолжает пытаться подключиться в фоне.
- Обрыв WS-соединения с Gateway в процессе матча — переподключение без потери
  уже накопленной ленты (ни в памяти, ни в файле).
- Повреждённая/нечитаемая строка в `chat_history.jsonl` при восстановлении —
  пропускается (лог ошибки в консоль), не должна ронять старт всего бэкенда.

## Тестирование

- `merge_event`: добавляет новое событие в `app_state["chat_events"]` и в файл;
  повторный `event_id` не дублируется; список обрезается по
  `MAX_CHAT_EVENTS_IN_MEMORY`.
- `load_chat_events`: читает JSONL-файл построчно, пропускает битые строки.
- Сам цикл подключения к Gateway WS (реконнект и т.п.) — тонкая связующая
  логика, аналогичная непротестированному `mqtt_transport.py` в референсном
  Gateway-репозитории; юнит-тестами не покрывается, проверяется вручную запуском
  с реальным (или временно недоступным) Gateway.

## Расположение в репозитории

- `web/backend/chat_feed.py` — `merge_event`, `load_chat_events`,
  `append_chat_event`, фоновая задача подключения к Gateway.
- `web/backend/config/chat_history.jsonl` — файл-журнал (создаётся при первом
  событии, не коммитится в git — добавить в `.gitignore`).
- `web/backend/tests/test_chat_feed.py` — юнит-тесты `merge_event`/
  `load_chat_events`.
- `web/frontend/index.html`, `styles.css`, `board.js` — новая панель ленты,
  изменение общего layout на двухколоночный.

## Открытые вопросы (не блокируют реализацию)

- Точный URL WS-эндпоинта Gateway строится из уже существующего
  `GATEWAY_BASE_URL` (замена схемы `http`→`ws`) — предполагается, что порт и
  хост совпадают с REST (как в реальном Gateway, проверено на локально
  поднятом инстансе во время бренсторминга).
