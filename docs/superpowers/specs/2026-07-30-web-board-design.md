# Дизайн: веб-морда, доска (v1)

Дата: 2026-07-30

## Контекст и цель

Основной deliverable проекта — веб-фронтенд («веб морда») для управления/наблюдения за
матчем (см. `CLAUDE.md`). Полный список требований к веб-морде (доска, лента переговоров
агентов, таймер хода, счёт/штрафы, статус Kill Switch) слишком велик для одной итерации —
эта спека покрывает только первую, самую нужную часть: **саму доску** — рендер, ручное
перемещение фигур и три режима работы. Остальное (лента переговоров, таймер, счёт) —
отдельные будущие итерации со своими спеками.

Формат доски и фигур согласован с уже спроектированным (но ещё не реализованным)
`move_validator` (`docs/superpowers/specs/2026-07-30-move-validator-design.md`), чтобы
подключить его позже без переделки структур данных.

Комплект фигур — полный стандартный (16 на 16), доска стандартная 8×8, клетки в
алгебраической нотации `a1`-`h8` (см. `CLAUDE.md`).

## Архитектура

Небольшой Python-бэкенд (FastAPI, в том же стиле, что и `sverk_ai_communication_server`
организаторов) плюс простой фронтенд без фреймворка — статический HTML/CSS/JS с доской,
отрисованной через SVG. Бэкенд:

- хранит единственное, общее для всех состояние доски в памяти (не в браузере) — несколько
  открытых вкладок/экранов видят одну и ту же доску одновременно;
- рассылает изменения состояния всем подключённым клиентам через WebSocket;
- в режиме 3 (см. ниже) сам обращается к Gateway организаторов
  (`sverk_ai_communication_server`, `POST /api/v1/messages`) — из браузера этого не делаем,
  чтобы не зависеть от CORS и сетевой доступности Gateway с произвольного зрительского
  устройства.

## Данные

```python
app_state = {
    "board": {
        "e2": {"color": "white", "piece": "pawn", "robot_id": "peshka-01"},
        "e7": {"color": "black", "piece": "pawn"},
        # ... только занятые клетки; "robot_id" присутствует только у наших,
        # привязанных к аппарату фигур — у фигур соперника его нет
    },
    "mode": "view",       # "view" | "correct" | "manual"
    "our_color": "white", # "white" | "black"
    "bindings": {
        "drone-01": {"piece": "king", "color": "white"},
        # статичная привязка аппарат -> фигура, задаётся один раз в конфиге
        # на весь матч, в рантайме не меняется
    },
}
```

Клетка/фигура описываются так же, как в `board_state` модуля `move_validator`
(`{"color": ..., "piece": ...}` по каждой занятой клетке), чтобы validate_move можно было
вызывать на этих же данных без конвертации, когда он будет подключён.

`robot_id` в `board` следует за фигурой при её перемещении: конкретный дрон/ровер остаётся
закреплён за одной и той же фигурой (королём, конём и т.д.) весь матч — привязка не
переприсваивается по клеткам, она переносится вместе с фигурой.

## Три режима поля

1. **Наблюдение (`view`)** — доска только отображается. Никакого drag-and-drop, запросы на
   перемещение отклоняются. Безопасный режим для зрительских экранов во время реального
   матча, когда никто не должен случайно сдвинуть фигуру.
2. **Коррекция позиций (`correct`)** — drag-and-drop разрешён для фигур **обеих сторон**, без
   проверки шахматных правил и без каких-либо обращений к роботам. Перетаскивание фигуры на
   клетку с чужой фигурой — взятие: чужая фигура снимается с доски. Цель режима — привести
   состояние доски в UI в соответствие с реальным физическим состоянием поля (например, после
   ручной коррекции судьёй), а не проверять или исполнять ходы.
3. **Ручные ходы для отладки (`manual`)** — тот же drag-and-drop, что и в `correct` (тот же
   локальный эффект на `board`), но если у фигуры на исходной клетке есть `robot_id`
   (то есть это наша, привязанная к аппарату фигура), бэкенд дополнительно отправляет в
   Gateway организаторов `POST /api/v1/messages` на этот `robot_id` с текстом:
   ```
   лети в клетку {to}
   ```
   (только целевая клетка, без исходной — упрощённая форма по сравнению с фразой, которую
   понимает pseudo-агент из репозитория `sverk_drone_agent`; точное соответствие форматам,
   которые понимают pseudo- и LLM-агент, нужно перепроверить на реальном железе — см. открытые
   вопросы). Если у фигуры на `from` нет `robot_id` (это фигура соперника), перемещение ведёт
   себя как в режиме `correct` — никакого обращения к Gateway, робота попросту нет.
   Ответ/ошибку от робота (или от самого Gateway) показываем в UI, не блокируя при этом уже
   применённое локальное изменение доски.

Режим — общее состояние на все открытые экраны (сервер-side), переключается любым из
открывших страницу (отдельной аутентификации/ролей не вводим — команда небольшая и доверенная).

## API

- `GET /api/state` — текущее полное состояние (`board`, `mode`, `our_color`, `bindings`).
- `WS /ws` — подписка на изменения состояния, сервер рассылает полное состояние при каждом
  изменении (без дифов — состояние небольшое).
- `POST /api/mode {"mode": "view"|"correct"|"manual"}` — переключить режим, разослать всем.
- `POST /api/our-color {"color": "white"|"black"}` — переключить, какая сторона наша.
- `POST /api/move {"from": "e2", "to": "e4"}` — попытка переместить фигуру с `from` на `to`.
  Поведение зависит от текущего `mode`, как описано выше. В режиме `view` возвращает ошибку
  «режим наблюдения — перемещения запрещены» и не меняет состояние.

## Обработка ошибок

- `view` отклоняет `/api/move` явной ошибкой без изменения состояния.
- В `manual`, если Gateway недоступен или робот ответил ошибкой/таймаутом — локальное
  состояние доски всё равно остаётся обновлённым (пользователь уже физически перетащил фигуру
  в UI), а ошибка показывается отдельно, не откатывая позицию. Отладочный режим не должен
  превращаться в блокировку UI из-за сетевых проблем.
- Перемещение с пустой `from`-клетки — ошибка, состояние не меняется (в любом режиме, кроме
  `view`, где перемещения в принципе отключены).

## Тестирование

Юнит-тесты на бэкенд-логику (без реального Gateway, HTTP-вызов мокается):

- режим `view` отклоняет `/api/move`;
- режим `correct` перемещает фигуру и снимает чужую при взятии, без обращения к Gateway;
- режим `manual` для клетки с `robot_id` вызывает мок Gateway с ожидаемым телом запроса
  (`robot_id`, текст `"лети в клетку {to}"`) и переносит `robot_id` вместе с фигурой на новую
  клетку;
- режим `manual` для клетки без `robot_id` (фигура соперника) ведёт себя как `correct`, Gateway
  не вызывается;
- ошибка/таймаут ответа Gateway в `manual` не откатывает уже применённое перемещение.

## Расположение в репозитории

- `web/backend/` — FastAPI-приложение (`app_state`, роуты, WebSocket, клиент к Gateway).
- `web/frontend/` — статические `index.html`/`board.js`/`styles.css` (SVG-доска, без сборки).
- `web/backend/tests/` — юнит-тесты.

## Открытые вопросы (не блокируют реализацию)

- Точный текст/формат команды, который надёжно распознают и pseudo-агент, и реальный
  LLM-агент на дроне («лети в клетку {to}» — рабочее предположение, взятое из ресёрча
  репозитория `sverk_drone_agent`), нужно перепроверить на реальном дроне.
- Аналогичный формат команды для роверов (ладьи) и диспетчера пешек ещё не подтверждён —
  сейчас предполагается тот же шаблон текста, адресованный соответствующему `robot_id`.
