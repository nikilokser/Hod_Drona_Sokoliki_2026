# Дизайн: авто-выбор хода через LLM-агентов (v1)

Дата: 2026-07-31

## Контекст и цель

Регламент требует, чтобы ход выбирался исключительно через взаимодействие
LLM-агентов (шахматные движки запрещены). Сейчас на веб-морде это никак не
автоматизировано: ход всегда вводится вручную drag-and-drop, включая
физическую отправку команды на дрон в режиме `manual`.

Задача — построить оркестратор, который: (1) просит сильную модель предложить
ход, (2) проверяет его локальным валидатором, (3) даёт агентам фигур на борту
дронов/роверов проголосовать по нему, (4) при необходимости регенерирует
предложение с учётом обратной связи, (5) исполняет принятый ход тем же путём,
что и сейчас ручной drag-and-drop в режиме `manual`.

Инфраструктура для этого частично уже есть и не строится заново:
`move_validator` (легальность хода), `gateway_client.send_fly_command`/
`apply_move` (физическое исполнение), Gateway организаторов
(`POST /api/v1/messages` с `wait_for_answer`/`answer_timeout_sec` — уже
поддерживает то, что нужно для голосования, см. `sverk_ai_communication_server`).
LLM-провайдер — `https://ai.sverk.io/v1`, тот же OpenAI-совместимый
`chat/completions`, под который уже заточен бортовой агент дронов
(`OPENAI_BASE_URL`/`OPENAI_API_KEY`/`OPENAI_MODEL` в `sverk_drone_agent`).
Сильная модель на ноуте — `deepseek-v4-pro`; слабые модели на бортах —
`gemma-4-31b` (или другая лёгкая из того же шлюза).

## Область действия

Включено: предложение хода сильной моделью, локальная валидация, рассылка на
голосование бортовым агентам, 3-вариантный формат ответа (да/нет/свой ход),
эскалация повторяющейся альтернативы, ограниченная регенерация, автоматическое
исполнение принятого хода, отображение процесса в UI.

Не входит в scope v1:
- **Ходы пешками.** Пешки управляются пока не построенным
  агентом-диспетчером на ESP-платах (см. `CLAUDE.md`) — ни голосования, ни
  автоматической физической отправки для них нет. Сильная модель ограничена
  промптом до короля/ферзя/слонов/коней/ладей; если всё равно предложит ход
  пешкой, оркестратор его отбрасывает на этапе локальной валидации, не считая
  использованной регенерацией, и просит другой ход.
- **Grounding-check позиции** («дрон думает, что стоит не там, где считает
  доска») — отдельная будущая задача (v1.1), требует изменения бортового кода
  для передачи `current_cell` в LLM-промпт. Сейчас этого нет ни у одного из
  двух путей бортового агента.
- Авто-триггер оркестрации по смене хода — в v1 только ручная кнопка.
- Верификация/поддержка агентного стека роверов — не блокирует: если
  `rover-01`/`rover-02` ещё не online с рабочим агентом, они просто не попадут
  в кворум голосования (см. ниже), без отдельного кода под этот случай.

## Кворум голосования — вычисляется динамически, не хардкодится

`GET /api/v1/robots` (уже обёрнут в `gateway_client.get_robots()`) отдаёт
online-статус и тип каждого робота. Кворум раунда = все `robot_id`, которые:
online **и** тип не `peshka` **и** привязаны (`bindings`) к нашей фигуре,
всё ещё стоящей на доске.

Это одним и тем же механизмом решает две вещи: роверы включаются в
голосование сами по себе, как только появятся online с рабочим агентом;
временно недоступный дрон (уже наблюдалось на sverk-8) автоматически выпадает
из кворума вместо того, чтобы блокировать раунд ожиданием таймаута.

## Алгоритм одного хода

Реализуется в новом модуле `web/backend/move_orchestrator.py`, единая функция
`async def propose_and_execute_move(app_state, broadcast) -> dict`, вызывается
из нового эндпоинта `POST /api/orchestrator/propose-move`.

1. **Контекст позиции.** FEN через уже существующий `stockfish_client.board_to_fen(app_state["board"], app_state["side_to_move"])`.

2. **Предложение сильной модели.** Запрос к `deepseek-v4-pro` на
   `https://ai.sverk.io/v1/chat/completions`, системный промпт явно запрещает
   ходы пешками и требует строгий JSON-ответ:
   `{"from": "e2", "to": "e4", "reasoning": "..."}`
   (паттерн как у `JSON_PLANNER_PROMPT` в бортовом `openrouter_host.py` —
   переиспользуется идея, не код, зависимостей на вендорский репозиторий нет).

3. **Локальная валидация.** Адаптер
   `to_validator_board(app_state["board"], app_state["side_to_move"]) -> {"board": {...}, "side_to_move": ...}`
   переводит `{"e2": {"color": "white", "piece": "pawn", ...}}` в формат
   `move_validator.board.py` (`{"e2": ("white", "pawn")}`), затем
   `move_validator.rules.validate_move`. Если нелегален или это пешка —
   причина уходит назад сильной модели, повтор (до 3 локальных попыток,
   без сети — не тратит бюджет регенераций из п.7).

4. **Кворум.** Как описано выше, через `get_robots()`.

   Если кворум пуст (все нужные роботы offline) — пропустить голосование
   целиком и сразу перейти к исполнению (п.9), с пометкой в UI «выполнено без
   голосования — кворум недоступен». Блокировать весь ход из-за связи хуже,
   чем повторить логику fail-open из п.8 на шаг раньше.

5. **Рассылка на голосование.** Новая функция в `gateway_client.py`:

   ```python
   def ask_robots(robot_ids: list[str], text: str, timeout_sec: float = 30.0) -> dict:
       payload = {
           "robot_ids": robot_ids,
           "text": text,
           "wait_for_answer": True,
           "answer_timeout_sec": timeout_sec,
       }
       # POST /api/v1/messages, тот же паттерн try/except HTTPError -> {"ok": False, ...}
       # что и в send_fly_command/send_chat_message.
       # Ответ Gateway — DispatchResponse: response["results"] — список
       # {"robot_id", "success", "answer", "status", "error", ...} по каждому
       # роботу (см. models.py TargetDispatchResult в sverk_ai_communication_server).
   ```

   Текст сообщения всем одинаковый: `[ГОЛОСОВАНИЕ] Позиция: <FEN>. Предложен
   ход <piece> <from>-<to>. Обоснование: <reasoning>. Ответь строго одной из
   строк: "ДА: <причина>", "НЕТ: <причина>" или "ХОД: <клетка>-<клетка>:
   <причина>".`

6. **Разбор ответов.** Для каждого `results[i]` с `success=True`:
   - строка начинается с `ДА` → да;
   - начинается с `НЕТ` → нет;
   - начинается с `ХОД:` → парсинг `<from>-<to>`, прогнать через тот же
     `move_validator.rules.validate_move` (позиция для проверки — текущая,
     альтернатива предполагается для того же хода, что и предложение
     сильной модели, то есть с той же стороны) — если нелегальна, выкинуть
     как шум, не считать;
   - что угодно ещё/не распарсилось → игнорировать как шум (не да, не нет).

7. **Решение по приоритету:**
   - если какая-то валидная `(from, to)`-альтернатива встречается **у ≥2**
     респондентов → эскалация: это предложение вместе с суммой причин
     уходит сильной модели как отправная точка для новой попытки
     (`Учти: N агентов предложили другой ход <from>-<to> по причине: ...`),
     возврат к п.2, счётчик регенераций `+1`;
   - иначе если есть хотя бы одно явное «НЕТ» → возврат к п.2 с причинами
     отказов в промпте, счётчик регенераций `+1`;
   - иначе (все «да» или нет ответов вовсе, кроме недостигшей порога
     альтернативы) → ход принят, к п.9.

8. **Лимит регенераций — 2.** После второй регенерации, если снова не
   получилось чистое «принято» — исполняется последний валидный (легальный,
   не-пешка) вариант предложения без дальнейшего ожидания консенсуса, в UI
   явно помечается `"consensus": "forced_after_regeneration_limit"`.

9. **Исполнение.** Переиспользуется существующая логика `POST /api/move` в
   режиме `manual` (`state.apply_move` + `gateway_client.send_fly_command`,
   обновление `side_to_move`) — не дублируется отдельной веткой кода, а
   вызывается как общая внутренняя функция (сейчас эта логика инлайн в
   `app.py::move`, при реализации вынести в переиспользуемую функцию,
   вызываемую и из `/api/move`, и из оркестратора).

## Формат ответа эндпоинта и отображение в UI

`POST /api/orchestrator/propose-move` возвращает объект-транскрипт раунда:
список попыток (`{"proposal": {...}, "votes": [...], "outcome": "escalated_alternative"|"vetoed"|"accepted"|"forced"}`),
финальный применённый ход, `state` (как у `/api/move`).

Транскрипт попадает в `app_state` как новый список
`app_state["orchestrator_log"]` (по аналогии с `chat_events` — усечение по
максимальному размеру, broadcast по WS целиком вместе с остальным состоянием)
и отображается в существующей ленте переговоров новым типом карточки
(`event_type: "orchestrator"`), либо отдельной секцией той же панели — решить
на этапе фронтенд-вёрстки, не блокирует бэкенд.

Новая кнопка «Предложить ход ИИ» в тулбаре — доступна только когда
`app_state["mode"] == "manual"` и `side_to_move == our_color` (те же условия,
при которых сейчас разрешён ручной перевод своей фигуры с диспетчем на
робота).

## Промпт на борту — только конфиг, без патча вендорского кода

Использовать существующий хук `AGENT_PROMPT_FILE` (`config/agent_prompt.md`,
уже поддержан в `agent_text_node.py`/`openrouter_host.py`). Дописать
инструкцию:

> Если сообщение начинается с `[ГОЛОСОВАНИЕ]`, это не команда полёта — не
> вызывай никакие инструменты. Ответь только одной строкой в одном из трёх
> строгих форматов: `ДА: <причина>`, `НЕТ: <причина>` или
> `ХОД: <клетка>-<клетка>: <причина>`.

Разворачивается тем же способом, что и патчи 0001-0003 (SSH на дрон,
редактирование файла, без пересборки — конфиг читается при каждом запуске
ноды). На модели голосования — `OPENAI_MODEL=gemma-4-31b` через systemd
override, аналогично уже существующему `DRONE_AGENT_MODE`.

## Обработка ошибок

- Сильная модель недоступна/вернула не-JSON → как и Stockfish-паттерн,
  `{"ok": False, "error": ...}`, UI показывает ошибку, ход не исполняется.
- Gateway недоступен при рассылке голосования → пустой/частичный список
  `results`, трактуется как пустой кворум (см. п.4) или как молчание части
  голосующих (не как «нет»).
- Таймаут ответа конкретного робота → тот же кейс, что и обычная недоступность
  ответа — не считается ни «да», ни «нет», просто не входит в подсчёт.
- Ход, предложенный сильной моделью пешкой → отбрасывается локальной
  валидацией, не расходует бюджет регенераций (см. п.3).

## Тестирование

- `to_validator_board`: конвертация из формата `state.py` в формат
  `move_validator.board.py` на известных позициях.
- Парсер голосов (да/нет/ход, включая мусорные/нераспознанные ответы) —
  чистая функция, тестируется без сети и без моков LLM.
- Правило приоритета (эскалация > вето > принято) и подсчёт порога `≥2` —
  чистая функция на синтетических списках голосов.
- `propose_and_execute_move` целиком — с моками `httpx`/LLM-клиента (как уже
  сделано для `stockfish_client.get_best_move` и `gateway_client` в
  существующих тестах), включая: чистое принятие, вето с регенерацией,
  эскалация альтернативы, исчерпание лимита регенераций (fail-open), пустой
  кворум, ход пешкой отброшен без траты бюджета.

## Расположение в репозитории

- `web/backend/move_orchestrator.py` — весь алгоритм: промпт сильной модели,
  парсер голосов, правило приоритета, цикл регенераций.
- `web/backend/gateway_client.py` — добавить `ask_robots`.
- `web/backend/state.py` или `app.py` — вынести общую логику исполнения хода
  (`apply_move` + `send_fly_command` + обновление `side_to_move`) в
  переиспользуемую функцию для обоих вызывающих (`/api/move` и оркестратор).
- `web/backend/app.py` — новый эндпоинт `POST /api/orchestrator/propose-move`.
- `web/backend/tests/test_move_orchestrator.py`.
- `web/frontend/index.html`, `styles.css`, `board.js` — кнопка «Предложить
  ход ИИ», отображение `orchestrator_log`.
- `patches/sverk_drone_agent/` — не патч кода, а обновление
  `config/agent_prompt.md` на каждом дроне (документировать в README рядом с
  остальными шагами разворачивания per-дрон).

## Открытые вопросы (не блокируют реализацию)

- Автоматический триггер оркестратора по смене хода (сейчас только кнопка) —
  отложено, добавить после обкатки ручного цикла вживую.
- Grounding-check реального положения дрона (v1.1) — требует патча 0004
  бортового кода, отдельная задача.
- Точный дефолтный таймаут ответа на голосование (`answer_timeout_sec`) —
  предварительно 30 с на агента, скорректировать по факту наблюдаемой
  задержки LLM-вызова на бортах (сейчас видели десятки секунд на некоторые
  ROS-сервисные вызовы, но голосование не должно требовать выполнения
  ROS-инструментов вовсе, так что задержка должна определяться только
  временем ответа LLM-провайдера).
